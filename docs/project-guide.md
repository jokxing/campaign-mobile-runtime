# Campaign Mobile Runtime：项目导览与面试讨论

更新：2026-10-14。本文说明作品定位、原项目个人贡献、核心实现和演示边界。历史经历依据本人确认，当前实现依据源码；当前代码能力不自动等于原项目中的个人成果。本轮只读复核并补充文档，未重新验收浏览器交互。

## 项目定位

当前作品使用 Nuxt、Vue、Vant 和 TypeScript，展示移动端配置驱动页面、接口分层、预览协议及消息交互。首页、活动中心、会员展示和消息会话使用模拟数据；`server/api` 是本地 HTTP/SSE Mock，不是独立生产业务后端。

与 MultiTenant Admin Lab 分别维护工程。后台编辑首页与活动配置，移动端负责运行时渲染，通过 iframe 消息协议预览。后台发布记录与移动端 Mock 数据的存储范围不同，不能据此宣称已完成线上发布或真实账号共享。

## 当前源码可确认的三条链路

### 1. 配置到首页与活动页面

首页按配置中的模块顺序渲染，并过滤隐藏模块；不同模块类型分别展示横幅、公告、快捷入口、内容网格和权益卡片。活动列表按分类、可见性和草稿状态筛选，详情按活动类型选择组件。

活动接口集中在 API 层，响应进入状态前检查配置结构。活动列表记录分类、滚动位置和条目锚点，返回时尝试恢复浏览位置。

| 入口 | 阅读重点 |
| --- | --- |
| [首页](../app/pages/home.vue)、[首页状态](../app/composables/useHomeRuntime.ts) | 模块顺序、显隐及类型分支 |
| [活动列表](../app/pages/campaigns.vue) | 分类、筛选、进入详情前保存位置 |
| [活动详情](../app/pages/campaign/%5Bcode%5D.vue)、[活动组件](../app/components/campaign/) | 按类型渲染、规则与样例进度 |
| [活动 API](../app/api/campaign.ts)、[加载器](../app/composables/useCampaignRuntimeLoader.ts) | 请求、运行时校验、状态提交和失败降级 |
| [列表恢复](../app/composables/useCampaignListRestore.ts) | sessionStorage、滚动及锚点恢复 |
| [首页模型](../shared/home.ts)、[活动模型](../shared/campaign.ts) | 配置契约 |

边界：会员中心以静态展示为主，活动进度包含固定演示值。资格判断尚未覆盖完整日期、草稿和隐藏活动约束，不能称为真实活动参与闭环。

### 2. 消息发送、失败反馈与事件刷新

前端通过具名 API 加载会话、发送消息并标记已读。发送时保留提交文本快照；成功后只有输入仍等于该快照才清空，避免删除发送期间新输入的内容。失败展示文字反馈并保留当前输入，中文输入法组合阶段的回车不触发发送。

详情请求使用序号判断结果是否仍有效；切换会话后，旧发送结果按会话标识过滤。列表刷新任务按 Nuxt 应用实例协调。SSE 事件通知重新获取数据，而非直接充当完整会话数据源。

刷新协调器复用进行中的 Promise；这段时间再收到失效通知会设置 pending，当前请求完成后继续刷新，而不是仅丢弃重复通知。这样覆盖“请求已取旧快照、期间又到新消息”的情况；它不是事件持久化或断线重放，不能保证恢复全部漏失事件。

发送接口成功后，仅在输入仍与提交时快照一致时清空，避免删除用户后来输入；Enter 还检查输入法组合状态。详情加载序号防止旧结果写回，但只比较会话 ID 的发送保护并不等于覆盖所有 A→B→A 切换竞态，不作穷尽保证。

### 后台服务台与本服务的关联

MultiTenant Admin Lab 的“客户服务会话台”通过本项目的 /api/support 接口读取列表/详情、标记 agent 已读、接入、回复及结束会话，并订阅同一 SSE 通知。服务端数据位于[内存仓库](../server/utils/support-store.ts)，两端只要指向同一 Nuxt 服务就共享客服状态；不是两个独立客服 Mock，也不代表已完成认证、持久化或多实例共享。

可在两端打开同一会话，依次客户发送、后台接入回复、客户读取、后台结束；这是待浏览器复核的源码路线。后台与移动端的异常保护并不对等：后台仍有发送前清空输入、旧详情响应和通知忙碌丢刷新等待办，不将本移动页的输入保留与序号保护扩大为后台也已实现。两端重启后历史不保证保留。

### 3. 后台配置到移动端预览

预览默认关闭，需要显式开启和配置来源白名单。移动端发送 `PREVIEW_READY`；收到后台配置时检查父窗口、精确 origin 和配置结构，合法更新再提交到首页或活动状态，非法更新保留旧配置。

## 五到十分钟体验路线

1. 运行项目，依次查看 `/home`、`/campaigns` 和一个活动详情，说明配置与类型组件的分工。
2. 在活动列表选择分类、进入详情后返回，观察分类与滚动恢复；这一步仍需要浏览器验收。
3. 查看 `/messages` 和会话详情，输入文本、模拟断网发送，观察反馈及输入保留，再恢复网络重试。
4. 对照 `app/api/support.ts`、共享契约和 Mock 路由，解释错误码、输入限制与状态规则。
5. 如展示后台关联，按白名单说明启动两端，在首页或活动编排中修改配置，观察 iframe 更新。

演示顺序最终应根据本人能说明的实际贡献调整。列表恢复、消息乱序及双端预览不因源码存在而自动视为验收通过。

## 设计与面试讨论

**你负责整个移动端吗？** 移动端主要由另一位同事负责。我主导 SaaS 后台，支援首页、客服的页面和功能，并与移动端同事约定首页组件字段。大部分 UI 组件由他实现，主要接口联调由他与后端共同完成。

**租户怎样得到不同首页？** 原业务根据租户需求设计组件，租户设置组件开关，启用的组件组成页面，并配置排序、素材和跳转。当前作品通过配置模型与类型组件演示这种思路。

**后台保存后会立即更新移动端吗？** 原项目采用后台发版后、移动端刷新请求接口取得配置的方式。当前 iframe 预览用于展示配置效果，不代表原项目的发布机制或线上部署完成。

**这个项目是 AI 写的吗？** 原移动端支援阶段以手写代码和 VS Code Tab 补全为主；当前作品使用 AI 辅助脱敏、提炼和整理。历史职责与当前新增实现分开介绍。

**为什么按活动类型拆组件？** 当前作品的通用页面负责加载、标题、资格展示和规则框架，类型组件处理不同活动内容，避免所有布局分支集中在一份模板。这里讨论当前实现，不将活动组件整体归为原项目中的个人成果。

**为什么 SSE 事件到了还要发 HTTP？** 当前事件主要携带类型与会话标识，完整记录由 HTTP 获取；事件触发合并刷新，减少连续通知带来的重复请求。这里描述本地 Mock，不推断原项目的通道设计。

**刷新过程中又收到消息怎么办？** 在当前请求后补一次刷新，避免请求复用时错过较新的状态。持续通知可能带来多轮刷新，不是固定一次请求，也不提供可靠事件日志。

**有 TypeScript 为什么预览消息还要校验？** postMessage 是运行时外部输入，类型声明不能约束窗口实际传来的数据。当前先检查开关、精确 origin 与窗口来源，再校验嵌套配置后克隆写入。此边界用于配置预览，不作为业务 API 身份授权。

**SSE 连接由谁关闭？** 当前移除页面监听器不会关闭模块级 EventSource，连接所有者和销毁策略仍是待办；不能仅因页面卸载有 removeListener 就声称连接资源已完整释放。

**发送成功后为什么不能直接清空输入框？** 用户可能在请求期间继续输入。成功后只清空仍等于提交快照的草稿，避免删除新内容；失败保留输入并展示错误。

**为什么前后端 Mock 共用校验器？** 字段限制、角色枚举和错误语义集中维护，减少模拟接口与前端理解不一致。模拟的 `sender`、`reader` 不是可信身份，真实后端仍须从认证会话推导。

**原项目经历与当前作品怎样区分？** 原项目分工按本人确认的实际模块介绍；当前的 Mock、预览校验、测试及工程优化按展示阶段实现说明，不用新增代码代替历史个人贡献。

## 当前需要保留的技术待办

- 活动加载器的 `inFlight`、缓存时间和请求标识仍为模块级变量；不同 context 的请求及 SSR 作用域需要复盘。
- 活动加载失败使用本地种子回退，仍标记 `ready`，成功与演示降级状态需要进一步区分。
- 列表恢复的存储结构校验和写入异常处理不完整；恢复效果需浏览器核对。
- 活动列表可见性、详情入口和参与资格规则需要统一，固定样例进度与真实业务数据区分。
- SSE 生命周期、断线恢复、快速会话切换和双端同步仍需交互验收。

这些待办是当前源码与已有清单的核对结果，本次只整理文档，未修改实现或重新执行构建和测试。历史验证见[优化清单](optimization-checklist.md#手动回归要求)，不能作为本轮验收结果。
