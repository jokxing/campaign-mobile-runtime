# 协作方式与项目演示

## 项目定位

面向前端 / 全栈偏前端岗位的作品：展示配置驱动页面、API 分层、Mock 契约、异常交互与可复现验证。没有独立业务后端，不将 Mock 描述为真实线上鉴权或生产服务。

## 异步协作约定

需求、接口、问题与验收结论记录在文档或任务卡中，关键决策保留可追溯记录。遇到不明确的需求，用“我的理解、影响范围、建议方案、待确认项”表达，确认后再修改契约。

该方式让双方都能回看上下文，减少重复说明。以下是项目提供的协作材料与模板，不代表已经发生过真实团队评审。

| 协作对象 | 提供的材料 | 希望得到的确认 |
| --- | --- | --- |
| 产品/设计 | 页面状态：正常、空、失败、重试、发送成功、会话关闭 | 文案、交互及验收场景 |
| 后端同事 | [API 契约](api-contract.md)、共享类型、Mock 示例、错误码 | 字段语义、身份推导、状态码、幂等与 SSE 策略 |
| 测试同事 | 自动测试命令、固定种子 ID、场景请求头 | 测试结果及未覆盖的设备/浏览器场景 |
| 评审同事 | [规范清单](optimization-checklist.md)、改动范围、已知限制 | 具体文件/场景上的反馈与结论 |

## 本次决策记录

- 背景：前端求职展示项目，所有数据使用 Mock。
- 决策：P0 聚焦契约校验、失败体验、可信预览和可执行验收。保留 Nuxt HTTP Mock，以便模拟真实前后端联调。
- 取舍：不新增账号系统、数据库或权限平台；401/403 是明确标注的模拟场景。共享校验器减少前端与 Mock 的字段分歧。
- 兼容影响：非法 sender/reader 不再默认为 customer，而是返回 422；预览默认关闭，联调要显式配置来源；不符合 v1 约束的旧配置会被拒绝。
- 待确认：真实接口接入时，由双方评审契约文档末尾的问题；当前没有虚构的“后端已确认”结论。

## 问题反馈模板

```text
标题：[模块] 操作 + 实际异常
环境：分支/版本、浏览器、页面路径
复现：1. ... 2. ... 3. ...
期望：...
实际：...（附文字日志、HTTP 状态及 data.code）
影响：受影响页面/用户操作
建议：...
待确认：需谁确认什么；确认后如何验收
结论：决定、负责人、日期（真实评审后填写）
```

## 五分钟演示路线

1. 展示首页、活动列表和详情，说明配置数据与展示组件的分工。
2. 打开 `app/api/support.ts` 与共享契约，对照 Mock messages 路由，说明参数、错误码和响应是怎样约定的。
3. 在消息会话中输入草稿，用浏览器 Offline 后发送：文字提示失败、草稿保留；恢复网络后重试。中文输入法选词回车不应误发送。
4. 按契约文档用请求头复现 403/503；说明它们是模拟验收场景。运行测试展示异常输入不会改变消息数据。
5. 展示预览白名单、嵌套配置校验和此协作文档，说明如何让同事复现问题、提出反馈、留下确认记录。

## 验证命令与人工验收

建议使用 Node 24（当前验证环境 24.16.0；单元测试直接运行 TypeScript 共享协议）。

```bash
npm test
npm run check:api
npm run typecheck
npm run build
npm run test:mock
```

`test:mock` 使用刚构建的 `.output`，启动独立本地进程和临时端口；测试数据只存在此进程，结束时关闭，不操作正在运行的开发服务。

待人工验收：移动端断网/恢复、中文输入法、发送时编辑草稿、快速切换会话、SSE 管理端同步、合法父页面更新与非法来源不更新。这些不能以单元测试和 HTTP 测试代替。

“构建 Nuxt 移动端配置驱动演示项目，按业务封装 API，建立前端与 Mock 共用的参数契约、错误码和配置校验；完善消息失败重试与草稿保留，通过自动化契约测试及联调文档支撑异步协作。”

介绍时结合自己能讲清楚的设计与测试结果；不添加未测量的性能提升、不将本地演示称为线上业务成果。
